# Pipeline trust-boundary audit — 2026-04-26

Triggered by T-359's mis-merge: the squash-commit landed on master with only `tests_red` step commits, yet the pipeline reported `ticket_done`. The pipeline state file had every downstream step marked `status:done` with `attempts:1` even though the events log shows them being **skipped as "already done"** in the same millisecond `tests_red` finished.

This is the third instance of "the orchestrator trusted state without verifying it" in two days. Rather than patch the symptom, this audit walks the full pipeline sequence, lists every trust boundary, and ranks the bugs.

## 1. The architectural premise (and where it breaks)

The pipeline state file `memory/pipeline/{ticketId}.json` is the **single source of truth** for what's been done on a ticket. Every step decision (run vs skip, succeed vs fail, ship vs block) reads from it. But:

- **The worker has full Write/Edit access to the entire file**, not just its own slot. A misbehaving worker can mark any step as `done`.
- **The orchestrator reloads the file from disk after the worker runs** (`pipelineState = await this.loadPipelineJson(ticket.id) || pipelineState` — pipeline.js:1614, 1618, 395, 411, 638). The reload is wholesale; the worker's writes for other steps replace the orchestrator's prior state.
- **No cross-check exists** between "this step's status says done" and "this step actually ran in this run." An orphaned `done` from a previous run, a hallucinating worker, or a self-heal worker rewriting the file all look identical to the gate.
- **The squash-merge happens whenever `pipelineState.status === 'done'`** with no verification that the actual implementation step ran or that tests_green saw `all_pass:true` *this run*.

That's the load-bearing weakness that produced T-359's mis-merge.

## 2. Trust map (who writes what)

| Field | Owner (should be) | Owner (today) | Verified by |
|---|---|---|---|
| `status` (top) | orchestrator | both | end-of-loop guard at pipeline.js:849 (works) |
| `started_at` / `created_by` | orchestrator | orchestrator | `loadOrCreatePipelineJson` (works) |
| `steps[X].status` | orchestrator (after gate) | **worker** writes it; orchestrator reads back | nothing — taken at face value |
| `steps[X].metrics` | orchestrator | orchestrator | n/a |
| `steps[X].artifacts` (test_files, files_changed, …) | worker | worker | gate via `validateStep` |
| `steps[X].completed_at` | orchestrator | **worker** | nothing |
| `report` | orchestrator | orchestrator | n/a |
| `auto_commit` | orchestrator | orchestrator | n/a |

Every "worker writes it" row that has "nothing" in the verified column is a trust hole.

## 3. The step-completion decision flow

Following pipeline.js processTicket from line 293 (top of step loop):

```
for each stepConfig in steps:
  1. existingStep = pipelineState.steps[stepConfig.name]
  2. if existingStep.status === 'done' || 'not_applicable' → SKIP
                                                          ↑
                                          this is what tripped T-359
  3. if existingStep.status === 'crashed' || 'blocked' → reset to pending, retry
  4. else: run worker
     a. spawnClaude(prompt, ...)
     b. worker writes pipeline JSON file freely
     c. pipelineState = await loadPipelineJson(...)  ← stomps everything
     d. validateStep(artifacts) — gate fires
     e. if pass: checkpointCommitStep, return
     f. if fail: shouldHeal? → selfHeal worker writes JSON again
```

The decision at step 2 trusts `pipelineState.steps[X].status` literally. There's no signal of "this is from this run" vs "this got written by a previous run or a different step's worker."

## 4. The squash-merge guard (what it actually checks)

pipeline.js:849-878:

```js
if (status === 'blocked' || 'failed' || blocked_at)        → don't merge
else if (any step.status not in {done, not_applicable, skipped}) → block
else                                                              → merge
```

So the merge fires when **every step's `status` field is one of `done`/`not_applicable`/`skipped`**. There is no cross-check that:

- `tests_green` actually emitted a `step_done` event this run
- `tests_green.all_pass === true`
- `implement.files_changed` is non-empty (or the ticket has reason to be a no-op)
- The squash-merge commit's tree includes the files declared by `implement`

T-359 hit this exactly. Skipped `tests_green` produced `status:done` (worker-written), passed the merge guard, landed on master with no test verification.

## 5. Ranked findings

### P0 — landed on master without verification

**F1. Worker can mark unrelated steps as done.**
*pipeline.js:1614 + many.* After a worker runs, the orchestrator reloads the entire pipeline JSON from disk and overwrites in-memory state. The worker can write `steps.implement.status='done'` while running tests_red, and the orchestrator will skip implement on the next iteration. **Caused T-359's mis-merge.**

Fix: replace wholesale reload with a scoped merge. After step X completes, only `steps[X]` is taken from the worker's file; other steps' status comes from the orchestrator's prior in-memory state. ~30 lines + tests.

**F2. Squash-merge has no per-step "was actually run this run" check.**
*pipeline.js:849-893.* The merge guard accepts a state where every step is `done`/`skipped`/`not_applicable`, regardless of whether the run actually executed those steps. With F1 fixed F2 becomes harder to hit but is still the right check.

Fix: track an in-memory `executedThisRun` Set per ticket. Before squash-merge, every step in `config.steps` that's not in `skip_conditions` must be either in that Set or have a corresponding `step_attempt_done` event in this run's window.

**F3. tests_green can be skipped silently and still pass merge.**
*The combined effect of F1+F2.* If tests_green is marked done without running, no test failures surface and the ticket ships.

Fix: tests_green specifically should refuse to be considered done unless its artifacts include `all_pass:true` AND `tests_after > tests_before` (or the ticket explicitly declared `tests_red.outcome === 'existing_test_covers'`).

### P1 — quiet correctness risks

**F4. `skip_conditions` is opaque to the gate.**
*pipeline.js:329-332 (search "step_skipped").* A step that's legitimately skipped (e.g. `root_cause` when `tests_red.outcome !== 'existing_test_fails'`) is recorded with `status:not_applicable`. But the same `not_applicable` value is what the worker can write to bypass a step it didn't run. The merge guard treats both identically.

Fix: distinguish "skipped by orchestrator condition" from "skipped because state said so." The former is set by the orchestrator with provenance; the latter should never happen.

**F5. `loadOrCreatePipelineJson` accepts any file as long as `created_by:'pipeline'`.**
*pipeline.js:950-968.* If a worker writes `created_by:'pipeline'` (it can; full write access), the orchestrator skips its only sanity-reset path. Same vector as F1.

Fix: `created_by` is a per-run token (UUID). On each run, the orchestrator stamps a fresh token; reloads accept worker writes only if the token still matches.

**F6. Self-heal prompt gives the worker the full pipeline state JSON.**
*pipeline.js:1823, prompts.js heal block.* The worker is asked to "fix the JSON" and given the whole thing as context. Sonnet's typical move when given a structured doc to fix is to rewrite the whole structure. That's how T-359's heal worker stamped `done` across implement/tests_green/review/docs_update.

Fix: heal prompts should scope the worker to its own step's slot, with the rest of the JSON shown read-only.

**F7. `checkpointCommitStep` runs after gate pass but before any squash-merge integrity check.**
*pipeline.js:1671-1683.* The step's commits land on the pipeline branch immediately. If subsequent steps are skipped due to F1, the pipeline branch ships with partial work into the squash-merge.

Fix: commits per step are fine; the squash-merge guard (F2) is where integrity has to be enforced.

### P2 — operational sharp edges

**F8. After a ticket fails, cwd lands on the failed pipeline branch.**
Already fixed in 35a4e6d via `git checkout master` post-rollback. Listed for completeness.

**F9. The orchestrator trusts the worker's reported `completed_at` timestamp.**
Workers regularly emit timestamps that are minutes ahead of wall-clock. Mostly cosmetic but produces wrong durations in reports.

Fix: orchestrator stamps `completed_at` itself; ignore worker writes to that field.

**F10. `loadOrCreatePipelineJson`'s "external file" detection (created_by ≠ 'pipeline')** resets only step statuses, not `report`, `auto_commit`, or `_reviewCycles`. An attacker with file-write access could pre-seed a forged report. Not a realistic threat for a single-user tool but worth noting.

## 6. Recommended fix order

1. **F1 + F2 + F3 together** (P0 — the mis-merge class of bugs). One PR. Covers the trust-hole that landed T-359 on master with skipped steps.
2. **F4 + F5** (P1 — close the "step state is forgeable" door from both sides).
3. **F6** (P1 — make heal scope-safe by construction, not by request).
4. **F9 + F10** (cosmetic / hardening).

T-359 is left in its current half-shipped state on master as a fixture. After F1-F3 land, re-running it should detect that `implement` and `tests_green` did not execute this run, refuse the merge, and surface the ticket as `blocked` with a clear reason instead of silently shipping.

## 7. What the canary will tell us

If we re-queue T-359 after F1+F2+F3 land:

- **Expected**: orchestrator detects implement/tests_green/review never ran in the previous (or current) run, refuses to mark the ticket done, and either re-runs the missing steps or blocks with a reason listing them.
- **Failure mode**: ticket squash-merges again with skipped steps. That means the fix didn't close the actual hole and we need another pass.
- **Bonus**: the fix may surface other tickets that previously slid through — historic mis-merges (if any) become visible because their pipeline state files don't match the executed-this-run set.

The canary is honest. We'll know within one ticket run whether the architectural fix actually plugged the hole or just moved it.
